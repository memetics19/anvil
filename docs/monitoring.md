# Monitoring and alerting

One place to see how every host and service is doing, how secure they are and how the
internet line holds up, and alerts that are worth reading when they arrive. Built (role
`monitoring`): metrics from every host, kept 90 days, Grafana, Wazuh's security alerts in
Grafana, the internet line, and every alert to ntfy through one Alertmanager.

## Set up

1. Add the VM to the site dict in Vault (`site.hosts.monitoring`, shaped like
   `site/site.example.yml`) and a gateway entry in `site.services`:
   `{name: grafana, host: hosts.monitoring.ip, port: 3000, scheme: http}`.
2. `anvil apply identity --tags authentik`. Authentik makes Grafana's OpenID Connect client
   and writes its secret into Vault (`grafana_client_secret`, next to its own).
3. `anvil apply tf`, then `anvil apply monitoring` and `anvil apply apps --tags caddy`.
4. Open `https://grafana.<gateway-domain>`. Authentik logs you in. Every member of the single
   sign-on group is a Grafana administrator.

Grafana's own `admin` login is the way in when Authentik is down. Its password is in Vault,
`kv/homelab/monitoring/grafana`, key `admin_password`, generated by the first run. Copy it
without showing it: `vault kv get -mount=kv -field=admin_password homelab/monitoring/grafana | pbcopy`.

What runs on the VM (compose project `/opt/monitoring`, images pinned by digest):

- **VictoriaMetrics** stores the metrics, 90 days.
- **vmagent** scrapes every 30 seconds: node_exporter on every host of the inventory group
  `node_exporter` and on the Proxmox host, by their lab addresses. A host added to that group
  is scraped from the next run. The secrets enclave runs no exporter: nothing may reach in.
- **Grafana** shows them. Only it is published, on the VM's lab address, for the gateway,
  Pulse and the admin sources (`port_guard`). It sends no usage reports and checks for no
  updates.

### Dashboards

Every dashboard is Grafonnet: Jsonnet in `dashboards/` at the top of the repository, one
`<name>.jsonnet` each, on the shared helpers in `lib/anvil.libsonnet` (the data source, panel
defaults, the grid). `make dashboards` builds them into
`ansible/roles/monitoring/files/dashboards/<name>.json`, which the role installs in the folder Lab. Commit both. CI rebuilds them and fails when the JSON
differs from its Jsonnet, or when a JSON file has no Jsonnet source. Grafana reads them every
minute and cannot save changes made in the UI: change the Jsonnet.

Grafonnet is pinned to a commit in `jsonnetfile.json` and `jsonnetfile.lock.json`. The build
fetches it into `vendor/`, which is not committed. The tools, once:

```sh
go install github.com/google/go-jsonnet/cmd/jsonnet@v0.22.0
go install github.com/jsonnet-bundler/jsonnet-bundler/cmd/jb@v0.6.0
```

The dashboards:

- **Lab**, Grafana's home page: the whole lab on one page. Hosts up, the internet, critical
  alerts and warnings firing, cameras recording, security events, then one row per host (up,
  uptime, CPU, memory, fullest disk), what is firing now and over time, CPU, memory, network
  traffic and ping time. The Dashboards menu at the top goes on to the others.
- **Hosts**: up and uptime, CPU, memory, disk space, load, network and disk traffic, per host.
- **Internet**: the line up now, uptime over 24 hours, 7 and 30 days, an outage timeline
  (internet, router, DNS), ping time, packet loss, DNS lookups through Pi-hole, web pages.
- **Security**: Wazuh's alerts (level 10 and up, critical 12 and up), hosts reporting, alerts by
  level over time, the top rules and hosts, failed logins, changed files and vulnerabilities.
- **Frigate**: Frigate up, cameras sending video, detector speed and recording space now, a
  camera timeline, frames per second per camera (received, processed, detected, skipped),
  detector speed, detections by camera and object, CPU and memory per camera, and disk space.

Frigate's metrics come from its own `/api/metrics`. Port 5000, Frigate's API with no login,
stays on the Frigate VM's loopback. nginx on its lab address (port 9711) answers that one
path, only to the monitoring VM and the admin sources, and every other path with 404. The
scrape drops the process command lines, which hold each camera's address.

## Security: Wazuh in Grafana

Grafana reads Wazuh's alerts straight from its indexer, through the OpenSearch data source
plugin (installed at a pinned version when Grafana starts). It reads as the user `grafana`,
which can only read (role `wazuh_server` makes it; its password is `grafana_reader` in
`kv/homelab/wazuh`). The indexer's certificate is checked against Wazuh's own CA. The indexer
answers only the monitoring VM, the gateway, Pulse and the admin sources (`port_guard`).

Wazuh sends every alert of level 10 and up to Alertmanager on the monitoring VM (a Wazuh
integration, `custom-alertmanager`), as `WazuhAlert` with the host and the rule. From there it
goes the way of every other alert: grouped, held back while its host is down, silenced in
Grafana, and sent to ntfy. Level 12 and up is critical, the rest warnings. Wazuh's own
dashboard stays, for digging into an alert.

## Internet

The blackbox exporter on the monitoring VM checks the line every 30 seconds:

- ping to the home router and to three public resolvers (1.1.1.1, 8.8.8.8, 9.9.9.9)
- a lookup of `example.com` through Pi-hole
- two web pages (Google's and Cloudflare's)

The internet counts as up while any public resolver answers. An outage cannot be pushed while
it lasts, because ntfy is out there too: the message comes when the line is back, and the
outage is on the Internet dashboard either way. Those records are the evidence for the ISP and
for the status page.

## Alerts

vmalert checks the rules in `ansible/roles/monitoring/files/rules` every minute. Alertmanager
groups what fires and sends it to ntfy:

- **Critical** goes to the topic `lab-critical` at once, at top priority, and again every
  4 hours while it lasts. A message also comes when it is fixed.
- **Warning** goes to the topic `lab-warning`, held for the morning window (08:00 to 09:00):
  a digest, one message per kind of alert.
- While a host is down, its other alerts are held back: one message per problem.

Grafana shows the firing alerts and sets silences (Alerting, the Alertmanager data source).
Every rule file is checked by vmalert before it is installed.

One-time setup: a write-only ntfy user for Alertmanager, its token in Vault. On the netbird
VM (`ssh -t ubuntu@<netbird VM>`), where `ubuntu` runs docker through sudo:

```sh
sudo docker exec -it ntfy ntfy user add alertmanager
sudo docker exec ntfy ntfy access alertmanager 'lab-*' write-only
```

Nothing logs in with its password, so any long random string will do. An ntfy admin reads
every topic already. A user who is not an admin also needs
`sudo docker exec ntfy ntfy access <your ntfy user> 'lab-*' read-only`.

Then make its token from the Mac and pipe it into Vault, so it never shows or lands in a
shell history. sudo on the VM takes its password from the Keychain on stdin, because a pipe
has no terminal to ask on. The url is ntfy's lab address, not the public name, so an
alert still gets out when the internet or the gateway is down:

```sh
source scripts/env.sh
t=$(security find-generic-password -s homelab -a vm-sudo-password -w |
  ssh ubuntu@<netbird VM> "sudo -S -p '' docker exec ntfy ntfy token add alertmanager 2>&1" |
  awk '/^token tk_/{print $2}')
if [ -n "$t" ]
then
  printf '%s' "$t" |
    vault kv put -mount=kv homelab/monitoring/ntfy url=http://<netbird VM>:8081 token=-
else
  echo "no token made, run the ssh line without awk to see why"
fi
unset t
```

Subscribe to `lab-critical` and `lab-warning` in the ntfy app, then `anvil apply monitoring`.

What each alert means and what to do:

### HostDown

Critical. node_exporter on a host has not answered for 5 minutes, so the host or its network
is down. Check the Proxmox web console: is the VM running, does its console answer? For a
Proxmox host, check its iDRAC or its screen.

### DiskAlmostFull

Critical. Less than 5% is free on a filesystem. Find what grew: `sudo du -xh --max-depth=2 /`
on the host. Remove it, or grow the disk (`anvil increase-disk <vm> <GB>`).

### DiskFillingUp

Warning. At the rate of the last 6 hours, a filesystem runs out of space in less than 3 days,
and less than 25% is left. Look at the Hosts dashboard's disk space panel to see when it
started, then as for DiskAlmostFull.

### MemoryNearlyGone

Warning. Less than 5% of memory has been available for 15 minutes. `top` or `docker stats` on
the host shows what uses it. Lower a container's limit, or give the VM more memory.

### RouterDown

Critical. The home router has not answered a ping for 2 minutes. Its power, the router or the
network to it is down. The internet alerts are held back while it lasts.

### InternetDown

Critical. Not one public address has answered a ping for 2 minutes, while the router answers:
the ISP's side is down. The message arrives when the line is back. Note the time on the
Internet dashboard, check the ISP's status, and raise the incident on the status page.

### InternetFlaky

Warning. More than 5% of pings to public addresses failed over 15 minutes. The Internet
dashboard shows when and how much. If it repeats, take the packet loss and ping time panels to
the ISP.

### WazuhAlert

Wazuh raised an alert of level 10 or more on a host (level 12 and up is critical). The message
names the host and the rule. Open the Security dashboard, or Wazuh's own for the full event,
and act on what the rule says: a login from somewhere new, a changed system file, a known
vulnerability. A rule that fires and needs no action is tuned in Wazuh, not silenced forever.

### FrigateDown

Critical. Frigate's metrics have not answered for 5 minutes while its VM is up, so nothing is
recorded. On the Frigate VM: `sudo docker ps` and `sudo docker logs --tail 50 frigate`. A
crash loop usually names a camera or a config line. `anvil apply frigate` puts the stack back.

### CameraOffline

Critical. Frigate has had no frames from a camera for 5 minutes. Check the camera has power
and network: ping it, and look for it in the router's client list. A camera that came back
with a new address needs its fixed address in the router again. Its stream in the Frigate UI,
under the camera's settings, shows the ffmpeg error.

### CameraSkippingFrames

Warning. Frigate skips more than half a frame a second from a camera, for 15 minutes. The
detector or the CPU cannot keep up, so motion there may go undetected. Look at the Frigate
dashboard's detector speed and CPU panels. Lower that camera's detect fps or resolution, or
give the VM more CPU.

### FrigateDetectorSlow

Warning. One detection takes more than 200 ms, for 15 minutes. Usually it takes about 50 ms
on the CPU detector. The VM is short of CPU: check the Hosts dashboard for the Frigate VM and
what else runs on its Proxmox node.

### FrigateStorageLow

Warning. Less than 10% of the recording disk is free. Frigate deletes the oldest footage
early to make room, so less history is kept. Shorten the retention in Frigate's config, or
grow the disk (`anvil increase-disk frigate <GB>`).

### MonitoringBlind

Critical. No host metrics have arrived for 10 minutes: vmagent or VictoriaMetrics is down, so
no other alert can fire. On the monitoring VM: `docker ps`, then `docker logs vmagent`.

## Before it

- **Pulse** checks that services answer and runs the public status page.
- **Homepage** shows a few live widgets.
- **The nightly `anvil drift`** pushes a message to ntfy when the lab no longer matches
  the code or a smoke test fails. The `security` smoke test is one of them: it looks for
  intrusion and mining on every host (tests/README.md). Run it by hand with
  `anvil test smoke security`. Schedule the nightly run once with `anvil drift --install`.
- **node_exporter** runs on the VMs and the Proxmox host, on the lab address. Nothing
  collected its metrics until vmagent.

What is missing:

- No history. When something is slow there is no graph to look at.
- No hardware alerts. A failed power supply on the second server was found by chance on
  the iDRAC page.
- No early warning for slow problems: a disk filling up, a ZFS pool degrading, a backup
  that quietly stopped.

## Goal

- Grafana is the only dashboard for metrics. Every dashboard is Grafonnet in this repo.
- An alert means a human should act. A quiet week has no alerts.
- Everything is code. `anvil apply monitoring` builds it, the same as any other service.

## The stack

A `monitoring` VM on the second server, next to the other new workloads.

| Part | Role |
|---|---|
| VictoriaMetrics (single node) | Stores the metrics. Less memory and disk than Prometheus for the same data. 90 days kept |
| vmagent | Scrapes every exporter and writes to VictoriaMetrics |
| vmalert | Evaluates the alert rules |
| Alertmanager | Groups, silences and routes alerts to ntfy |
| Grafana | Dashboards. Behind the gateway, logging in through Authentik (OpenID Connect) |

What is scraped:

| Exporter | What it shows |
|---|---|
| node_exporter, upgraded and bound to the lab address | CPU, memory, disks, network on every VM and both Proxmox hosts |
| pve-exporter, with a read-only Proxmox token | VMs, storage and the cluster as Proxmox sees them |
| Ceph's own exporter (mgr module) | The Terraform state store |
| ZFS and SMART | Pool health and disks that are starting to fail |
| A Redfish exporter for both iDRACs | Power supplies, fans, temperatures, hardware events |
| cAdvisor | Each container's CPU and memory |
| A small backups exporter | The age of the newest Vault, Vaultwarden, Authentik and Terraform state backup |

Pulse stays as it is. It owns "is this service up" and the status page. The new stack
owns metrics and everything else. Each problem has exactly one owner, so it never alerts
twice.

## Alerts that are not noisy

These are the rules, not suggestions. A rule that breaks them is changed or removed.

1. **Alert on symptoms a person must act on.** A disk that will be full in three days,
   not a CPU spike. A failed power supply, a degraded pool, a sealed Vault, a backup older
   than 36 hours, a certificate that expires in 14 days.
2. **Every alert waits before it fires.** It has a `for:` duration, so a short blip never
   wakes anyone.
3. **Two levels only.**
   - Critical: pushed to the phone at once. Something is broken now.
   - Warning: one morning digest. Something needs attention this week.
4. **Grouped and inhibited.** One message per problem, not one per symptom. When a host is
   down, the alerts for the services on it are held back.
5. **Quiet during planned work.** `anvil apply` sets a silence for the hosts it touches
   and lifts it when it ends. The nightly drift check does not alert during an apply.
6. **Every alert links to its fix.** Each rule names a section of the docs that says what
   it means and what to do.
7. **Reviewed monthly.** Any alert that fired and needed no action is tuned or deleted.
   The aim is fewer than one critical alert a week.

## Steps

1. Done: a `monitoring` VM on the second server (Terraform, the same pattern as the others).
2. Done: the node_exporter role upgraded and bound to the lab address. The other cluster
   members do not run it yet.
3. Done: VictoriaMetrics, vmagent and Grafana. Grafana behind the gateway with Authentik.
4. The exporters above, one at a time, each with its dashboard as a JSON file.
5. Done: vmalert and Alertmanager with the first small rule set: host down, disk full and
   filling, memory, and monitoring blind. ZFS and SMART, power supplies, backups,
   certificates and Vault sealed come with their exporters (step 4).
6. `anvil apply` silences, and the drift check routed through Alertmanager.
7. Two weeks of tuning before more rules are added.
